### Real-device evidence — two properties confirmed

Arinzechukwu supplied specific device observations on the corrected Android
preview build. Recorded here as confirmed evidence for exactly two plan-first
properties, and no more than two.

**1. Biometric/device-credential re-entry — CONFIRMED.** Logged in, left the app
for a few minutes, reopened it, and was correctly required to present a
fingerprint before regaining staff access. This genuinely exercises the gate:
`session.tsx` sets `status = "locked"`, which routes to `/unlock`, whose only
path back is `unlockStaffSession()` → `LocalAuthentication.authenticateAsync`.
There is no bypass around that call, so a real fingerprint prompt is proof the
lock engaged and that the OS credential is what released it. The lock also
clears `staff` state and removes every `["staff", …]` query from the cache
before the prompt appears.

One deliberate precision note: the observation proves the biometric requirement
but does not by itself distinguish *which* of the two lock triggers fired.
Backgrounding for more than two minutes and returning fires the `AppState`
`elapsed > 2 * 60 * 1000` branch; a force-kill and relaunch fires the
cold-restore branch (cached token present, `staff === null`). Both are
plan-first requirements and both terminate in the same biometric gate, so the
biometric property is closed either way. The app remaining in the recents
switcher (see below) points to the background path. The >2-minute *threshold*
specifically — that a return inside two minutes does NOT prompt — is not proven
by this test and is the one cheap negative control still worth taking.

**2. App-switcher content obscuring — CONFIRMED.** Verified through Android's
recent-apps switcher that staff content is obscured in the thumbnail rather
than legible. This exercises `ScreenCapture.enableAppSwitcherProtectionAsync(1)`,
which is registered only while `principal === "staff"` and
`status === "authenticated"`, and is torn down on cleanup. Confirmed for
Android; iOS is untested and the plan-first scopes this as "where the OS
supports it".

Not confirmed by this observation: `preventScreenCaptureAsync("staff-session")`,
the separate screenshot block, which was not separately exercised.

## Staff mobile CP2 — teacher attendance, device gate pending

Implemented CP2's two screens plus the temporary marking rail. **No server
change**: no migration, no route, no permission, no `ALL_PERMISSIONS` entry.
Gate 0 tested that claim rather than asserting it, against real Postgres.

Gate results:

- **Gate 0** — `getTeacherScope` supplies arm name + class-level name in one
  call; `getRegister` supplies fullName, admissionNumber, status, markedAt and
  markedBy, and carries none of `dateOfBirth`, `address`, `phone`, `email`,
  `bloodGroup`, `medicalNotes`, `guardians`, `photoUrl`. The no-server-change
  boundary holds.
- **Gate 1** — the arm list is `formTeacherArmIds ∩ classArms`, so a subject
  teacher is never offered a register the service would 403. Two distinct empty
  states: "you teach here but are not a form teacher" vs "no classes assigned".
- **Gate 2** — dirty-rows-only submit through the single atomic endpoint. No
  optimistic write, no queue. On failure the edits are kept but nothing is
  redrawn as saved, and `ApiNetworkError` reads as "never left the phone",
  distinct from a server refusal.
- **Gate 3** — `staff-keys.spec.ts` asserts the ACTUAL keys the screens build
  (`["staff", schoolId, userId, …]`) resolve to `mayPersistQuery === false`,
  and enumerates `queryKeys` so a future staff key cannot escape the spec.
- **Gate 4** — exactly one audit row per submit (not one per student); a
  dirty-only re-submit changes the touched row, leaves the untouched row's
  `markedAt` byte-identical, keeps the day at two records (upsert, not append),
  and writes a second audit row so an amendment is never invisible.

The temporary rail is `marking-window.ts`, one deletable file, documented as
temporary in both the file and the module doc. Two implementation notes:

- **"Today" comes from the server's HTTP `Date` header**, recorded by
  `apiFetch` on every response including failures, not from the handset clock —
  a rail reading the phone's own date is one a wrong phone clock walks around
  silently. No new endpoint, so the no-server-change boundary survives. With no
  response seen yet, marking is blocked rather than falling back to the device.
- **UTC, not Africa/Lagos.** The instruction referenced "the bursar dashboard's
  Africa/Lagos handling", but there is no Africa/Lagos date handling anywhere in
  this codebase: `dashboard.service.ts` computes in UTC with a comment saying
  local-time mutators would be the bug, `parseIsoDate` builds UTC midnight, and
  `resolveTermForDate`'s future-date check compares UTC midnights. The rail
  follows that, so client and server share one calendar. Lagos is UTC+1 with no
  DST; the two differ only between 00:00 and 01:00 local, outside school hours.
