## Findings

- F-02A is confirmed by source inspection. `ReportCardBoard` exposed a direct
  owner/admin `Release arm` click with no confirmation. The client posts to
  `POST /report-cards/arm/release`; `ReportCardWorkflowService.release()`
  changes every card in the `(termId, classArmId)` batch from
  `PRINCIPAL_APPROVED` to `RELEASED`, writes the audit row, and queues PDF
  rendering in the same tenant transaction. `ReleasedResultsService` filters
  both guardian and student reads to `status: RELEASED`, so this is the point
  at which their released-results surfaces become eligible to show the data.
- F-02B is not an implementation omission against an established report-card
  requirement. `NotificationDispatchService` supports lock-screen-safe push
  or SMS routing and finance uses it, but the report-card module neither
  imports nor calls it. Phase 6 documents a safe future wording ("Your school
  has released a new report card") but does not decide a release fan-out.
  Email, SMS and push have different readiness/cost/privacy concerns; release
  must remain independent of a notification failure. No notification behavior
  was added.

## Change

- Added a Release confirmation that identifies the class arm, term and known
  report-card count, explicitly says that release publishes to the relevant
  families/students, and distinguishes the consequential action from
  dismissal. The dialog disables both actions while the request is in flight;
  it closes only after the server-backed board state changes.
- Added persistent, role-aware workflow guidance for DRAFT,
  SUBJECT_REVIEWED, FORM_REVIEWED, PRINCIPAL_APPROVED, RELEASED, and the
  defensive mixed-state case. It states what is happening, who acts next and
  whether the viewer needs to do anything; release/reopen wording does not
  promise that family visibility can be undone.
- Added a Playwright regression spec that seeds an isolated local school/card,
  verifies dismissal sends no release request, verifies confirmation is needed
  before the request, and holds the intercepted request to assert duplicate
  submission controls. After the deliberate confirmation it marks only that
  disposable local card released so the normal board refresh can complete; the
  fixture is removed in `finally`.
