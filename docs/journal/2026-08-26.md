## D16 — SETTLED: keep option (a), the client-side term chain

Decided against the real number rather than the abstract worry.

**~4-5 seconds to first figures, and the chain is not most of it.** The cold
open covers app launch, secure-store token restore and the biometric/lock
path, then `/academic-years` → `/academic-years/:id/terms` → `/finance/dashboard`.
Only two of those requests exist because of D16. At a plausible 300-600 ms
round trip on Nigerian mobile data, the term chain accounts for roughly
0.6-1.2 s of the 4-5 s — real, but a fifth to a quarter of it. Removing it
server-side would leave a ~3.5-4 s cold open, not an instant one.

**The cost is also paid once per cold start, not per glance.** `useTermContext`
holds a 10-minute `staleTime`, so moving between Collections and the debtor
list, or returning within the lock window, does not repeat it.

**Against that, option (c) is expensive in the way that matters here.** Making
`termId` optional with a server-side current-term default would reopen a
decision `dashboard.dto.ts` records as deliberate, change behaviour for the web
finance pages as well as mobile, and break the mobile-only property that CP2
and CP3 have both held. That is a real architectural change to buy back
something under a second.

**Verdict: (a) stands, and now on evidence rather than by default.**

**Recommended follow-up, client-side, no server change:** prefetch the term
context on the staff home screen rather than on Collections open. The chain is
sequential by necessity, but it does not have to sit on the critical path — by
the time a bursar taps Collections, the answer could already be cached. That
would take most of the 0.6-1.2 s off the observed number without touching the
server contract. Not done here; logged as the cheap win if the cold open ever
becomes a complaint.

**Limits of this measurement, stated so it is not over-read:** one observation,
one device, one network, one school with twelve students and three invoices. It
is enough to settle a decision that was otherwise going to be settled by taste,
and not enough to be called a benchmark. If CP4 or a larger school makes the
cold open feel worse, re-measure before re-deciding.

## Copy school ID on the platform-admin dashboard

Small UI addition, no plan-first (same category as prior low-risk UI work).
Closes the deferred entry "Rollout rails make the operator fish the school ID
out of DevTools" (captured 2026-08-25 during CP2 Gate 5 prep, when the dry-run
could not be run without asking the maintainer to fetch the id by hand).

**What shipped.** Each school row's name cell in
`apps/web/src/components/super-admin/platform-admin-dashboard.tsx` now renders
a second line: a copy-icon button whose visible label is the full school id in
monospace. Clicking copies the id and swaps the icon to a tick for two seconds.
The id text itself never changes on copy — only the icon does — so the row does
not shift under the operator's cursor mid-click. A `role="status"` sr-only
element announces the copy for screen readers.

**Clipboard fallback.** `navigator.clipboard.writeText` can be refused
(insecure context, permission policy), so a failed write falls back to
`window.prompt` with the id pre-filled — the same pattern
`components/settings/invitations-table.tsx` already uses. Worth stating why the
fallback is not optional here: the affordance exists precisely so that
obtaining a school id never requires DevTools, and a silent clipboard failure
would hand the operator straight back to the Network tab.

**The id is rendered visibly, which diverges from what the deferred note
suggested** ("deliberately NOT a plain visible id column"). The note's concern
was row density and it was a fair one, but it is answered by placement rather
than by hiding: the id is a secondary line under the school name, not a ninth
column. The reason to show it is the note's own argument — the
operator-reviewed id IS the safety check `set-staff-mobile.ts` enforces via
`--confirm-school-id`. A copy-only icon would let an operator paste an id they
never looked at, which fails that check in a different way than typing one from
memory fails it. Seeing and copying are both needed for the check to mean
anything.

**Verification — real browser, real stack.** Chromium via Playwright against
the local NestJS API and Postgres, logging in through the actual
`/super-admin/login` form as a genuine platform admin (an e2e-provisioned owner
with `is_platform_admin` flipped in the database). Three assertions, all
passing:

1. the school id renders as text in the row — no DevTools;
2. clicking the button places THAT EXACT id on the clipboard, read back with
   `navigator.clipboard.readText()` under granted clipboard permissions;
3. the copied-state feedback appears and then reverts.

A row screenshot caught a real layout defect the assertions could not: the
36-character id wrapped onto two lines inside the narrow name column.
`whitespace-nowrap` fixed it and the check was re-run. Worth noting as a
reminder that a passing DOM assertion is not a rendering check.

**The spec was deliberately not committed.** It was written as a throwaway. Two
reasons: it seeds a platform admin by raw-SQL-flipping `is_platform_admin` on
an e2e owner, which duplicates fixture logic that does not exist yet in a
reusable form; and it adds ~30 s to an e2e job that already runs 3 minutes, to
guard a static affordance with no state machine behind it. If a platform-admin
session fixture is ever added for other reasons, this is a cheap test to
reinstate on top of it.

## Process finding — the D16 settlement was pushed to an already-merged PR

Recorded because it cost the project a materially wrong record on `main` for
several hours, and the failure mode is invisible if you check the things that
are normally worth checking.

**CORRECTION (same day).** This section originally claimed PR #216 was
"squashed from a state older than its branch head" and that the squash
"captured only the first" of three commits. Both claims were wrong, and the
timestamps say so plainly. The corrected account follows. The original wording
is preserved nowhere except in this paragraph, deliberately — a wrong
explanation of an incident is worse than no explanation, because it teaches the
wrong lesson.

**What actually happened.** The three commits were made at:

| Commit | Committed (UTC) | Content |
|---|---|---|
| `9d72617` | 01:19:48Z | CP3 implementation + module doc |
| `76ca052` | 01:20:21Z | Gate 5 as maintainer-reported (41 journal lines) |
| `2cb1184` | **02:20:13Z** | Gate 5 on device evidence + D16 settled (61 journal lines) |

PR #216 was merged at **02:11:16Z**. The squash `2bc013e` therefore captured
`9d72617` and `76ca052` — **both commits that existed at the time**, which is
exactly correct behaviour. The third commit was created **nine minutes after
the merge** and pushed to a branch whose PR was already closed. Nothing ever
merged it, because there was no longer an open PR to merge.

GitHub's squash was not stale and lost nothing. The mistake was entirely
mine: I committed the D16 settlement onto a merged branch and reported it as
landed without re-checking that the PR was still open. The pre-existing note in
my own status report — "`mergeStateStatus` returned `UNKNOWN`, GitHub
recomputing after the push" — was me misreading an already-`MERGED` PR as one
still settling.

**The visible symptom.** `main` carried CP3's code alongside a module doc that
still read *"Gate 5 maintainer-reported with figures pending"* and *"**D16
remains open** — it was to be decided on the cold-open measurement, which has
not been recorded."* Those sentences were `76ca052`'s, and they were accurate
when written at 01:20Z; they went stale an hour later and nothing updated them,
because the update never merged.

**Why it went unnoticed.** The post-merge check was `mergedAt`, `mergeCommit`
and five green checks — all genuinely fine, and all answering a question that
was not the one at risk. None of them says *whether the branch still has
unmerged commits on it*.

**Nothing was ever at risk of being lost.** `2cb1184` was pushed to
`origin/phase-6/staff-mobile-collections` and stayed there, a normal reachable
commit on a branch nobody deleted, backed up wherever the remote is backed up.
It was never dangling, never gc-eligible, never dependent on a local reflog. The
loss was of *visibility*, not of data: the settlement was on the server the
whole time, just not on `main` where anyone reading the project's record would
look. That distinction is worth keeping straight — "recoverable" and "recorded"
are different properties, and only the second one was broken.

**CP3's shipped code was never affected**, and this is checkable rather than
assertable. `git diff origin/main 2cb1184` over every non-docs path returns
nothing for CP3: all twelve mobile/API files are byte-identical between what
merged and what the branch held. Both lost commits were `docs/`-only — 41 and 61
journal lines plus a one-line status edit each. No mobile screen, no API
endpoint, no DTO, no migration, no permission was ever in question. The bug was
in the record, and only in the record.

**The check that would have caught it**, and is cheap enough to make routine
after any squash-merge:

```
git diff --stat origin/main <branch-head>   # must be empty
```

Empty means the branch has nothing left on it. That single command catches both
the "squash flattened less than you thought" case and the real one here —
"you kept committing after the merge" — without needing to know which happened.

**A second, related failure the same day.** The follow-up branch for the
copy-school-ID work was cut without checking out `main` first, so it branched
off the un-squashed CP3 branch and re-proposed CP3's commits against a `main`
that already had them. GitHub marked the PR `DIRTY` and — the part worth
remembering — **never scheduled its `pull_request` CI run at all**. A conflicted
PR does not fail CI; it silently has none, which reads as "no failures" to any
check that counts red marks rather than counting checks. Fixed with
`git rebase --onto origin/main <last-cp3-commit>`. Both incidents share one
root cause: acting on a branch without first confirming what it was based on.
