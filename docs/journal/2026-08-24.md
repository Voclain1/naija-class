# 2026-08-24

## Staff mobile companion — CP1 implementation, device gate pending

Started `phase-6/staff-mobile-auth` from deployed `origin/main`; the unrelated
untracked root `app.json` remains untouched. Added the approved staff-mobile
plan at `docs/modules/staff-mobile-companion.md`. No attendance, collections,
or dashboard workflow screen has started.

The database now distinguishes WEB/MOBILE staff sessions, stores a random
install id and human device label for mobile, enforces the mobile device shape
with a CHECK constraint, and defaults `School.staffMobileEnabled` false.
Mobile login and 2FA use dedicated routes. Redis challenge payloads bind the
STAFF_MOBILE audience and exact device, and the school flag is re-read both at
password acceptance and challenge completion. Mobile TTL is configurable but
clamped to seven days. Session list/revoke is caller scoped, omits token/IP/UA,
writes an attributed audit, and invalidates Redis immediately. A platform-admin
endpoint plus dry-run/exact-confirmation CLI provides the one-school rollout
rail.

The app recognizes guardian/student/staff, requires enrolled OS credentials
before saving a staff token, locks on cold restore and after more than two
minutes backgrounded, enables screenshot/app-switcher protection, never
registers staff push, and independently prevents staff query persistence by
both query metadata and the `staff` key prefix. The web Security page lists
safe session metadata and can revoke remote sessions.

Real local evidence: migration deployed to PostgreSQL; focused API suites pass
56/56 over real Postgres/Redis, including flag-off control, audience/device
rejections, flag-off-during-challenge, DB constraint rejection, 168-hour clamp,
cross-tenant revocation denial, exact audits, and direct Redis eviction.
Mobile tests pass 108/108. API/mobile/web typechecks and linters pass; mobile
web export succeeds; optimized web build succeeds (only the standing
Sentry/OpenTelemetry dynamic-dependency warning). Expo Doctor is 21/21 after
SDK 57 patch alignment and removal of the project-local legacy EAS CLI.

CP1 is NOT complete. EAS upload was subsequently authorized and the Android
preview ran on a real phone. The first login attempt found a real client bug:
the staff wrapper JSON-encoded its body before the shared client encoded it
again. The API therefore received a JSON string instead of an object. Both
login and 2FA now pass objects to the shared encoder, with exact wire-body
regressions; the full mobile suite is 110/110 and typecheck/lint remain clean.

The corrected APK then reached the next boundary and returned `Cannot POST
/api/v1/auth/mobile/login`. An independent, correctly encoded production probe
confirmed HTTP 404: the preview profile is production-bound, while CP1's API
route and migration are not deployed yet. This is a sequencing gate, not a
second client defect. Ship the rollout-disabled schema/API through the normal
PR and deployment path, then use the already-corrected APK against a reviewed
test school to finish biometric/PIN, cold restore, two-minute re-lock,
app-switcher protection, and remote-revoke evidence. No real school was
enabled and no workflow screen has started.
