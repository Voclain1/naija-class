## Payment links implementation — CP4 complete

Completed the admin invoice payment-link experience. The page renders the
server's connect-Paystack, not-created, creating, retryable-failure and live
states. A live link is read-only and copyable, and its WhatsApp action uses an
encoded `https://wa.me/?text=…` URL with no recipient. The message contains
the school name, server-fixed outstanding amount, student display label and
durable Paystack URL; no guardian email or phone is read or transmitted.

The real Chrome gate exercised the same tenant-scoped invoice as owner, admin
and bursar. Owner/admin passed immediately. The first bursar pass exposed a
real defect: because bursar intentionally lacks the separate student-read
permission, the page's generic student lookup failed and the share message
fell back to the raw student UUID. The fix moved the display label into the
payment-link DTO, populated by a tenant-scoped server lookup. The final bursar
URL contained `Chioma Nwosu (NJC/2025/003)` and never the UUID; no permission
was widened. The browser also proved the copy action returned the exact
durable URL and all five lifecycle states rendered against real database rows.

Focused payment-link lifecycle/share tests pass 8/8 after the fix; the
standing RBAC gate passes 2/2 and permission coverage passes 141/141. API/web
typechecks and lints, `git diff --check`, and the full optimized web build all
pass (including dynamic `/finance/invoices/[id]`; only the pre-existing
Sentry/OpenTelemetry critical-dependency warning remains). CP5 deployment and
staged rollout is next.

## Payment links implementation — CP5 rollout rail ready

Compared the payment split backfill directly with the established AI
one-school enablement discipline. The existing payment tool required reviewed
school ids but still accepted several ids in one invocation, leaving a batch
footgun. It now accepts exactly one school, has no blanket mode, and requires
apply-time repetition through `--confirm-school-id` as well as an active
platform-admin actor for the audit row. Tests pin zero-school rejection,
multi-school rejection, mismatched confirmation rejection and the valid
single-school control.

Real command-path evidence (not only the parser unit) invoked the shipped
backfill entry point with two `--school-id` values. It exited non-zero before
any database or Paystack operation with: “Pass exactly one operator-reviewed
`--school-id` … The rollout is one school per invocation.” The rollout/parser
and existing Paystack contract suites pass 21/21; API typecheck, lint and
`git diff --check` pass.

The runbook now makes the pilot gate explicit: dry-run one school, apply one
school, rerun read-only for a fresh remote split verification, prove the exact
audit count, then complete link/create/reload/share/payment/webhook/database/
archive smoke evidence before choosing the next school. Wider rollout is the
same observed sequence repeated, never a blanket flip.

## Virgo pilot — Paystack greeting defect caught

The live Virgo Fidelis pilot proved split creation, durable-link creation,
WhatsApp sharing and school-name display, but exposed the per-link synthetic
email in Paystack's parent-facing greeting. Code inspection confirmed names
were already sent as `SchoolKit` / `Payment`; the proposed “just add names”
fix was therefore already present and ineffective.

Real test-mode API and hosted-page evidence closed the behavior directly.
Paystack accepted duplicate Customer records for the same synthetic address,
so link isolation does not require a UUID-bearing email. Payment Request
`PRQ_m9h11vo6o8sd25j`, created with `parent@schoolkit.ng` plus names `Parent` /
`School Fees`, rendered exactly “Hey parent@schoolkit.ng,” on the real hosted
page. New links now use that stable, non-PII, human-readable address. Virgo's
existing UUID-bearing live request must be archived and recreated after this
fix deploys; it must not be shared with a parent.

Both test requests used for the investigation (`PRQ_8tumrx7wz0s935b` and
`PRQ_m9h11vo6o8sd25j`) were archived through the real test API with HTTP 200.
The focused payment-link integration suite passed 7/7, including an exact
assertion on the new email and names; API typecheck and focused lint also
passed.
