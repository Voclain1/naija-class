# 2026-08-22 — standing RBAC two-gate conformance gate (PR 1)

Implemented the first, behavior-neutral PR from
`docs/modules/rbac-two-gate-reconciliation.md`: I1 (no permission enforced by
a handler is orphaned from every seeded staff role) and I2 (a seeded role
grant cannot be made inert by the service's role list).

The spec is `apps/api/src/__tests__/rbac-two-gate-conformance.spec.ts`. It
compiles the real `AppModule`, discovers controller instances from Nest's
`ModulesContainer`, and follows each handler's actual injected service
instance. There is no hand-maintained handler-to-service table. TypeScript's
AST is used only to read the allowed-role literal from the resolved service
method; an unresolvable gate fails instead of silently dropping out.

First run evidence:

- I1 found no orphaned permission enforcement.
- I2 found exactly 20 disagreements: 15 teacher grants blocked on general
  academic/roster read paths, four owner/admin grants blocked on teacher-self
  endpoints, and one teacher `report-card.comment` grant blocked on the
  principal-note service path.
- Classification found all 20 to be deliberate scope/principal restrictions,
  not live authorization bugs. They are recorded in the gate as six explicit,
  reasoned design-exception groups: five teacher-scope/principal-note groups
  plus the inverse rule for pure owner/admin callers of teacher-self routes.
  The I2 assertion independently requires zero undocumented disagreements,
  zero stale exceptions, and zero duplicate exception entries. Dual-role
  owner/admin+teacher users remain valid because the service role gate is
  any-of; no production behavior changed.

Verification: the final focused Vitest spec passes (2/2) with zero
undocumented disagreements, API typecheck passes, and API lint passes.
`isActive`, all production role checks, the ~89-site cleanup, and payment-link
work remain untouched. The pre-existing untracked root `app.json` was not

## Payment-link final spike and plan-first (PR #203)

Closed the last Paystack uncertainty with real `sk_test_` API calls. One
`percentage: 100` Transaction Split (`SPL_TJ5TvoYt9w`) was accepted by two
Payment Requests at different amounts (123,400 and 987,600 kobo). The same
split then settled two successful test-mode authorization charges at those
amounts: SchoolKit's integration share was zero both times; the school
subaccount received gross less Paystack fee. This proves the split is
amount-independent and reusable across all of one school's invoices. Flat,
amount-specific splits are rejected from the design.

Both temporary Payment Requests were archived and the temporary split's only
subaccount was removed; the two test transactions remain in Paystack's test
ledger as the evidence trail. No test helper was retained in the repository.

Rebased docs-only PR #203 onto current `main` and completed
`docs/modules/shareable-payment-links.md`. The final plan now pins: nullable
`School.paystackSplitCode`; verified split creation during assisted setup;
dry-run/idempotent existing-school backfill; a FORCE-RLS durable link model;
synthetic `noreply-payment-<opaque-id>@schoolkit.ng` Paystack customers;
metadata-based `paymentrequest.success` correlation without a new SECURITY
DEFINER function; archive-pending handling for every invoice balance change;
no-recipient `wa.me`; visible connect/retry states; five gated implementation
checkpoints; and a final 4–6 focused-day estimate. No product implementation

## Payment links implementation — CP2 complete

Added the durable `PaymentLink` model and API lifecycle on
`feat/payment-links`. Migration `20260822170000_payment_links` creates a
FORCE-RLS table and a partial unique index over `CREATING` plus `LIVE`, so the
database reserves an invoice before the external call and prevents two
concurrent creators. GET exposes discriminated connect/not-created/creating/
retry/live states; POST re-checks the caller's active owner/admin/bursar role,
revalidates invoice balance and school routing server-side, uses only a
synthetic `noreply-payment-<link UUID>@schoolkit.ng` customer, persists
correlation-only metadata, fetch-verifies Paystack before exposing the URL,
and writes one success audit without creating a `PENDING Payment`.

Real local-Postgres evidence paired valid controls with the rejection: tenant
A insert succeeded, tenant B could not see it, tenant B's attempted tenant-A
insert was rejected by the RLS policy, and tenant B's own insert succeeded.
The runtime connection returned zero rows without its tenant GUC. Two separate
concurrent transactions against one invoice yielded exactly one success and
one Prisma `P2002`, leaving one active row.

Real Paystack test-mode evidence created and independently fetched Payment
Request `PRQ_qa8y451u4uvb63p` for 345,600 kobo through persisted split
`SPL_RzjgpOl0Jl`. Amount, NGN currency, customer, split and metadata ids all
matched; local state contained the exact tenant id, zero Payment rows and one
audit. Cleanup archived the request, removed the split's subaccount and
deleted all synthetic database fixtures. The synthetic Paystack customer
record remains in the provider's test customer ledger because this integration
has no customer-deletion operation; it contains no guardian PII.

A negative lifecycle test proves a mismatched Paystack fetch is archived and
becomes `CREATE_FAILED` with no URL, no success audit and a bounded retryable
failure response. Verification: focused CP2 real-DB suite 5/5; Paystack and
invoice regression suites 52/52; permission coverage and standing RBAC gates
143/143; API typecheck, lint and `git diff --check` pass. CP3 is next.
