## Work log

### Real `RESEND_API_KEY` set — first real test surfaces a second, different blocker

Arinzechukwu provided a real Resend API key. Set via `flyctl secrets set
RESEND_API_KEY=... -a school-kit-api`, confirmed deployed via `flyctl
secrets list`.

Verification discipline carried over from the R2 fix two days ago: don't
just confirm the secret is present, prove a real send. Reused Arinzechukwu's
own real test guardian (`kingvoclain@gmail.com`, at "Virgo Fidelis
Montessori School" — a genuine record from his original bug report, not a
QA artifact) rather than fabricating fresh test data. His original July 20
invitation was already accepted, so a fresh `invite()` call wouldn't hit
`INVITATION_ALREADY_PENDING`.

Booted the actual production NestJS app inside the live container
(`NestFactory.createApplicationContext(AppModule)` — real DI, real env,
not a stub) and called the real `GuardiansService.invite()` directly.
Result: progress, but not success — the code now genuinely reaches
Resend's API (no more "not configured" error), but Resend rejected the
send outright:

```
The schoolkit.ng domain is not verified. Please, add and verify
your domain on https://resend.com/domains
```

`EmailService` hardcodes `from: "no-reply@schoolkit.ng"`; Resend requires
DNS-level domain verification (SPF/DKIM) before it will send from a given
domain, independent of whether the API key itself is valid. No email
reached the guardian. The invite still succeeded at the application level
(best-effort design, unchanged) — a real accept link was produced and left
in place, since it's genuine guardian state, not test data to clean up.

**Isolated the API-key path from the domain problem specifically** —
worth doing before reporting back, per the standing "hard evidence, not a
theory" discipline this whole sweep has followed. Sent a one-off email
directly via the Resend SDK (bypassing `EmailService`, no code changed)
using Resend's pre-verified fallback sender, `onboarding@resend.dev`.
First attempt (to the guardian's address) was rejected by Resend's own
platform rule: unverified-domain accounts can only mail the account
owner's own address. Retried against that address instead — **succeeded**,
real Resend email id returned. Confirms the key/integration mechanism
itself was already fine; the domain was the only remaining problem.
Couldn't independently check final delivery status via Resend's own API —
the key is deliberately scoped send-only, so `emails.get()` returned `401
restricted_api_key`.

Logged as **partially fixed, not resolved** in `docs/deferred.md`, with
the full evidence trail (PR #108) — deliberately not marked done, per
explicit instruction not to conflate "key works" with "delivery works."
Flagged domain verification as the one remaining step, needing
Arinzechukwu directly (Resend dashboard + `schoolkit.ng`'s DNS — neither
`flyctl` nor anything else in this session's toolset reaches either).

### Domain verified — re-test, clean send, confirmed real delivery

Arinzechukwu verified `schoolkit.ng` in Resend (SPF/DKIM records added).

Re-ran the identical test. One wrinkle: the pending invitation created by
the *first* test attempt (this morning, before verification) was still
outstanding (`acceptedAt: null`), so a fresh `invite()` call hit
`INVITATION_ALREADY_PENDING`. Deleted that one stale row directly
(`db.guardianInvitation.deleteMany({ where: { guardianId, acceptedAt:
null } })`, 1 row — the failed attempt's own leftover state, not
Arinzechukwu's real accepted invitation from July 20, which was untouched)
and called `GuardiansService.invite()` again, same production app context,
same real guardian, `warn`/`error` logging enabled — the same levels that
had clearly surfaced the failure twice already.

This time: no `EmailService` error, no `Guardian invite email failed`
warning — only the pre-existing, unrelated `TermiiService` SMS warning
(Termii itself remains a separate, still-open gap). Clean `INVITE RESULT`
with a fresh accept link.

**Arinzechukwu confirmed the email actually arrived in his real inbox.**
That's the bar this whole sweep has held to throughout — not "no error
was thrown," but a human checking a real result. `docs/deferred.md`
updated to `[x]` fully resolved with the complete trail: both failures,
the domain-verification step, and this final confirmed delivery (PR #109).
